# 更新包容器与存档优化（`container` / `mca`）

这一篇讲两件事：**更新包用什么装**、**存档怎么装得更小**。两部分都是"无损"
的——玩家装完得到的文件与开发者打包前的文件**逐字节相同**。

相关代码（都很小、可单独拿出去看）：

| 文件 | 做什么 | 行数 |
|---|---|---|
| `app/core/container.py` | 块压缩容器（v2）的读写，兼容旧 zip | ~500 |
| `app/core/mca.py` | 存档 region 文件的"去 zlib 外壳"变换 | ~250 |
| `app/core/packwriter.py` | 导出时统一写包（两条导出路径共用） | ~180 |
| `app/core/packsign.py` | 完整性签名的算法与口径 | ~90 |

---

## 一、为什么 zip 不够

整合包的字节构成（实测，用真实模组 jar 拼的 211 MB 包）：

| 内容 | 占比 | 说明 |
|---|---|---|
| `mods/*.jar` | **82%** | 已经是 deflate 压缩过的 zip |
| `config/` | 6% | 文本，好压 |
| `resourcepacks/`、`shaderpacks/` | 8% | 已压缩 |
| `saves/`（若勾选） | 11% | `.mca`，**大有可为** |

zip 每个成员独立 deflate、窗口 32 KB，看不到"这个 jar 和那个 jar 里有同一份
库"这种跨文件冗余。换成"大块 solid + 128 MB 窗口"能再省一截，而且解压更快：

| 方案 | 体积 | 导出 | 解压 |
|---|---|---|---|
| zip deflate-6（= 启动器导出的做法） | 195.81 MB | 9.7 s | 1.9 s |
| **v2 容器（开启「Osmium 超级压缩」时）** | **184.92 MB** | 48 s | 4.5 s |

> 4.5 s 里有 ~2.6 s 是"还原存档外壳"的 CPU；不含存档的包解压只要 1.5 s 左右。

体积 **−5.6%**，对 1 GB 的整合包就是少下 50 MB。

> 默认导出仍是旧版 ZIP（旧客户端可读）；只有打开「Osmium 超级压缩（beta）」才会
> 写 v2 容器并对存档做去壳变换。压缩级别用 17：22 档只再省 0.08% 左右，
> 耗时约 6~9 倍。

## 二、v2 容器的格式

设计目标有三个：能**随机读**、能**并行解压**、能**边写边算签名**（不用回读整包）。

```
偏移 0      magic  "EAPK2\r\n\x1a\n"（9 字节）
偏移 9      u32  header_offset      索引块的绝对偏移
偏移 13     u32  header_comp_len    索引压缩后长度
偏移 17     u32  header_raw_len     索引原始长度
偏移 21     u32  format_version     = 2
偏移 25     blocks                   每个块是一个独立的 zstd 帧
header_off  zstd(json 索引)
```

索引长这样：

```json
{
  "format_version": 2,
  "block_size": 67108864,
  "blocks": [[压缩后长度, 原始长度], ...],
  "entries": [
    {"name": "modrinth.index.json", "size": 1234, "stored": 1234,
     "sha1": "…", "transform": null, "chunks": [], "inline": true},
    {"name": "overrides/mods/a.jar", "size": 5321, "stored": 5321,
     "sha1": "…", "transform": null,
     "chunks": [[0, 1048576, 5321]]},
    {"name": "overrides/saves/w/region/r.0.0.mca", "size": 2650112,
     "stored": 9000000, "sha1": "…", "transform": "mca",
     "chunks": [[1, 0, 9000000]]}
  ],
  "inline": {"modrinth.index.json": "base64…"}
}
```

几个关键点：

* **索引在尾部**：写的时候不需要预留头部空间，也不用二次拷贝整包；
  开头 25 字节只是个指针。
* **块 = 定长切片**：文件数据按顺序拼成一条流，每 64 MB 切一块，各自压。
  所以"只读一个文件"只需要解压它跨越的那几块。
* **元数据内联**：`modrinth.index.json` / `ea_settings.json` /
  `ea_hashes.json` / `changelog.md` 这类小文件直接 base64 放进索引 →
  导入时"只看元数据"是 **2 ms**（不用解压任何块）。
* **`transform` 字段**：目前只有 `"mca"`，见下一节。读取时自动还原，
  上层（比对、应用、校验）完全看不到差别。

### 兼容

`open_container(path)` 看前 9 字节：不是 `EAPK2` 就退回 `zipfile` 读取，
所以 0.12.x 及更早导出的包仍然能打开。写新包时若环境里没有 `zstandard`，
`PackWriter` 自动写 zip（`requirements.txt` 里已带，正常不会触发）。

### 可调参数

| 参数 | 默认 | 说明 |
|---|---|---|
| `DEFAULT_BLOCK` | 64 MB | 越大越接近 solid，压缩率略好；代价是解压时的内存峰值 |
| `DEFAULT_LEVEL` | 17 | 228 MB 素材上：15 → −5.0%、17 → −5.6%、19 → −6.0% 但慢一倍 |

实测 8 / 32 / 64 / 128 / 单块 之间体积差 < 1%，64 MB 是平衡点。

## 三、存档优化：去掉"逐区块的 zlib 外壳"

### 为什么有效

Minecraft 把每个区块单独 zlib 压一次再写进 `.mca`。这对存档本身是必要的，
但对"把存档打进更新包"是有害的：压缩器看到的是已经被 zlib 打散的字节，
跨区块的相似性被外壳隔断。

实测（真实 1.20.1 地形世界，24.7 MB / 4093 区块）：

| 处理 | 结果 | 占原始 |
|---|---|---|
| zip deflate-9 | 14.18 MB | 57.4% |
| xz -9e（≈ 7z） | 13.75 MB | 55.7% |
| **剥掉 zlib 外壳 + zstd/xz** | **8.86 ~ 7.54 MB** | **35.8% ~ 30.5%** |

### 怎么保证不把存档弄坏

1. **只剥外壳**，不解析 NBT、不改任何语义。
2. **逐字节可逆**：`restore(strip(x)) == x`，所以玩家端继续用原来的 sha1 校验，
   不需要"特殊文件"分支。
3. **扇区尾巴也要存**：MC 只覆盖新记录的长度，扇区尾部残留的旧字节不清理；
   不管空扇区（`file_len` 之后）还是扇区尾，都必须原样保留，否则复原出来的
   不是同一份字节。
4. **导出时自校验**：真的跑一遍 `restore` 比对 sha1，不一致就原样存
   （`strip_region` 返回 `None`）。所以"别的 MC 版本 / 服务器改过
   `region-file-compression-level`"的存档不会被弄坏，只是不享受优化。
5. 只处理 `region/` 与 `poi/` 下的 `.mca/.mcr`；`entities/` 是另一套结构，不碰。

### 变换流格式

```
"MCAR1" | u32 原始文件长度 | u32 区块数 | 8192 字节 region 头
逐区块： u8 压缩类型 | vint 裸NBT长度 | 裸NBT | vint 尾巴长度 | 尾巴
空洞：   vint 段数 | { vint 起点 | vint 长度 | 字节 } ...
```

还原时按 region 头的偏移表逐区块写回，压缩类型不变、zlib 档位用 6
（实测 1.20.1 的存档与 zlib-6 输出逐字节相同；4093/4093 全部一致）。

### 代价

还原要把 96 MB 裸 NBT 重新 zlib 压缩一遍：24.7 MB 世界约 **2.6 s**（单线程）。
所以导出选项里给了独立开关 `world_transform`，世界特别大的用户可以关掉。

## 四、签名怎么跟着变

`packsign.py` 里有两代口径：

* **v2（当前）**：逐条 `(文件名, 大小, 内容 sha1)`。写着的时候顺手就记下来了，
  不需要把包读第二遍——老的实现为了签名要把整个包重新读一遍。
* **v1（0.10.x 及更早）**：`(文件名, 大小, CRC32)`，只用于校验老包
  （CRC 能被构造碰撞，所以不再用于新包）。

存档变换对签名是**透明**的：`entries` 里记的是"逻辑内容"（还原后的 `.mca`）
的体积和 sha1，和玩家端校验的口径一致。

## 五、怎么单独用这两块（脱离本项目的例子）

```python
# 写一个容器
from app.core.container import ContainerWriter

with ContainerWriter("out.eapack", level=17) as w:
    w.add_inline("modrinth.index.json", b'{"formatVersion":1}')  # 内联元数据
    w.add_file("overrides/mods/a.jar", "/path/to/a.jar")          # 普通文件
    w.add_file("overrides/saves/w/region/r.0.0.mca",
               "/path/to/r.0.0.mca", transform="mca")            # 存档去外壳

# 读
from app.core.container import open_container
with open_container("out.eapack") as r:
    print(r.names)
    data = r.read("overrides/saves/w/region/r.0.0.mca")   # 自动还原
```

```python
# 只想要"去外壳"这一层
from app.core import mca
blob = mca.strip_region(open("r.0.0.mca", "rb").read())   # None = 不适合变换
raw = mca.restore_region(blob)                            # 与原始文件逐字节相同
```

这两块都不依赖 GUI、不依赖数据库，可以单独复制到别的项目里用。

## 六、实测汇总（228 MB 真实素材，含 24.7 MB 真实存档）

| | zip | v2 容器 |
|---|---|---|
| 包体积 | 195.81 MB | **184.92 MB（−5.6%）** |
| 导出耗时 | 9.7 s | 48 s |
| 解压耗时 | 1.9 s | 4.5 s（其中 ~2.6 s 是存档还原） |
| 读元数据 | 6 ms | **2 ms** |
| 逐文件 sha1 复核 | 0 处不符 | 0 处不符 |
| 存档还原一致 | 9/9 | **9/9（逐字节）** |

## 七、还能往哪儿优化

1. **增量补丁**（下一步，收益最大）：玩家已经有上一版文件时，只发
   `zstd --patch-from` 的补丁。实测同一模组换版本：oculus 补丁只有新文件的
   **6.6%**，superbwarfare **23.3%**。这比任何压缩器都有效，而且我们本来就知道
   玩家本地文件的哈希（扫描时核对过）。
2. **文件排序**：同样内容按不同顺序进块，zstd 结果能差 1.3%。可以按"同目录
   同前缀"聚簇，进一步贴近 solid 的上限。
3. **存档还原并行**：zlib 会释放 GIL，按 region 文件多线程能把这 2.6 s 压到
   ~0.8 s。
4. **存档的可选二级优化**（谨慎）：丢掉"全空气 section"和 `Heightmaps`
   还能再小 2~7%，但会改变存档内容（虽然游戏会重算），需要单独开关 + 充分测试。
